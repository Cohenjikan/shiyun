# 投稿开放可行性调研(2026-11)

> 来源反馈:#82 #90 #91 #92 #93 #128(6 条,均为「想把自己写的诗放进诗云」)。
> 本文**只调研,不含功能代码**。**第 1 节不是法律意见**,是公开资料整理,拿不准处已标注。

## 结论先行

**建议:近期不开放公开投稿(方案 C 否决);可选择性试行方案 B「只收稿、人工精选、静态入库」,但要先补齐三件事再开。**

1. 待验证的两个假设,一个成立、一个不成立:
   - 「热度已下降」**成立**:日均真人 UV 从 6 月均值 8,442(峰值 6/24 当天 30,242)降到 10 月均值 773,降幅约 91%(相对峰值约 97%)。
   - 「国内对这个平台监管可能不严格」**不能作为前提**。访客 **85% 来自中国大陆**,境外服务器 + 无备案并不等于规定不适用(见 §1)。实际执法以屏蔽为主,但一旦开放公开发布,站点就从「静态古诗星图」变成「面向大陆用户的 UGC 发布平台」,被拦截的概率和后果都明显上升,而诗云最值钱的正是大陆访客。
2. 架构上,投稿和两条红线(云端不存诗、语料全静态、字库双射不变)可以协调,但只适用于「人工精选后静态入库」这一种形态(§3)。
3. 滥用风险是真实的:8–9 月反馈接口上的测试和 XSS 探测(30 条)已经多于真实反馈(7 条)。公开展示面会直接放大这类风险(§4)。

## 1. 合规(不是法律意见)

逐条出处和原文摘录见附录 [`UGC-COMPLIANCE-NOTES-2026-11.md`](UGC-COMPLIANCE-NOTES-2026-11.md),其中【法规要求】【实际执法】【二手】【不确定】都有标注。下面是摘要。

### 1.1 法规要求(中国大陆)

| 规定 | 适用前提 | 对 UGC 的核心义务 |
|---|---|---|
| 网络安全法(2025-10 修改,2026-01-01 施行,**条号已变**) | 境内建设、运营、使用网络 | 信息发布服务要求用户真实身份(旧第 24 条);发现违禁信息停止传输、保存记录、报告(旧第 47 条 → 新第 49 条);网络日志留存不少于 6 个月(旧第 21 条)。新条号中第 23、26 条是推算,未核对重新公布的文本 |
| 互联网信息服务管理办法(292 号令) | 境内从事互联网信息服务 | 非经营性须备案;电子公告服务的记录保存 60 日;未备案的处罚是责令改正、拒不改正关闭网站 |
| 互联网论坛社区服务管理规定(2017) | 境内提供论坛社区服务 | 审核、巡查、应急处置制度;「后台实名、前台自愿」;违法信息处置并报告;举报入口 |
| 互联网跟帖评论服务管理规定(2022 修订) | 境内提供跟帖评论(含留言) | 后台实名;**只有新闻信息的跟帖强制先审后发**,诗歌投稿不属于此类 |
| 网络信息内容生态治理规定(2020) | 境内网络信息内容生态治理 | 平台须有信息发布审核和实时巡查制度;「平台」没有规模门槛 |
| 个人信息保护法、网络数据安全管理条例 | **有域外条款**:境外处理境内自然人个人信息、以向境内提供服务为目的 | 只有收集邮箱、微信号等联系方式时才触发 |

要点:论坛社区、跟帖评论、内容生态治理三份规定和 292 号令都以「境内」为前提,没有域外条款。「面向境内用户、服务器在境外」算不算「境内提供」,法规没有写明,也没有查到权威解释(**不确定**)。

### 1.2 实际执法情况(境外服务器、无备案、境外个人站长)

- 网络安全法旧第 50 条(新第 52 条)授权对「来源于境外」的违禁信息采取技术阻断,这就是 GFW 的明文依据。对境外站点**最现实的后果是被封**(DNS 污染、SNI 阻断),而不是处罚。
- **没有查到**境外个人站长因普通 UGC 被追责的公开案例。已公开的境外追诉都是网络攻击或政治类案件,不能类比。
- 站长本人入境大陆、或在大陆有家人和资产时,可能有次生风险。这一条只是推测,没有来源。
- **Cloudflare**:官方文档承认大陆访客由境外节点服务,延迟更高、可靠性更低;它的中国境内网络只对企业版开放,并且要求 ICP 备案。**Turnstile 在大陆不受支持**,投稿页如果用它做人机验证,大陆用户会提交不了。
- 没有找到「单纯无备案就会被封」的证据(**不确定**)。

### 1.3 澳大利亚

- Online Safety Act 2021:公开展示用户内容的站点会落入「指定互联网服务」这类兜底范围。eSafety 可以发**24 小时移除通知**(第 88 条网络欺凌、第 77 条私密影像),执行条款明文延伸到境外行为。方案 C 才会成为这类通知的对象。
- Basic Online Safety Expectations 没有强制约束力。没有查到 eSafety 对小型个人站点的执法记录(**不确定**)。
- Privacy Act 1988:年营业额 300 万澳元以下的小企业一般豁免;以非经营身份运营的个人是否算「组织」,没有核实(**不确定**)。

### 1.4 版权

- 澳大利亚的法定避风港**不覆盖一般在线平台**(司法部 2022 年议题文件)。个人运营的公开投稿站不能指望避风港,只能靠审核和及时下架。
- 方案 B 下站长把投稿收进语料,自己就是**直接发布者**,没有避风港可言。所以需要书面授权(建议用非独占、免版税、作者保留著作权、可申请下架的许可),入库前也要自己查重。
- 中国民法典第 1195、1197 条规定了「通知—必要措施」,未及时处理的对扩大部分承担连带责任。

### 1.5 对方案的含义

| 方案 | 大陆合规 | 澳洲合规 | 版权 |
|---|---|---|---|
| A 不开放 | 低 | 低 | 低 |
| B 只收稿、人工精选、静态入库(投稿原文不公开) | 低:不构成「信息发布平台」;不收联系方式就不触发 PIPL | 低:没有公开 UGC,移除通知没有对象 | 中:站长是直接发布者 |
| C 公开展示 | 中高:落入平台语境;主要后果是被封 | 中:可能收到移除通知 | 中高:没有澳洲避风港 |

**「监管可能不严格」这个判断,只在「不会对境外个人罚款或追诉」这一层大致成立。** 对诗云真正的约束是「被封就失去 85% 的访客」,这个风险随公开 UGC 显著上升,和监管是否严格关系不大。

## 3. 架构冲突与协调方案

### 3.1 冲突点

| 现有约束 | 投稿带来的冲突 |
|---|---|
| 隐私红线(`docs/DEPLOY.md` §7):云端不存诗、不存可逆编号;用户协议写明「诗文……只保存在你的浏览器」 | 投稿必须把诗文发到服务器,至少要临时保存,与现有承诺的字面和精神都冲突 |
| 语料全静态,前端只读静态分片 | 公开发布需要动态写入或频繁重建、重新部署;全量重建加预压缩成本很高(上次约 5 小时) |
| 字库双射:`N = 22,219`,编号由字库算出,所有 `#p=` 和拾遗编号依赖它 | 投稿诗里只要出现字库外的字,并入字库就会改变 N,全部编号失效(#89 用户已经抱怨过一次) |
| `poetId = fnv32(name|dynasty)` | 投稿人笔名可能和真实诗人同名同朝代(比如 dangdai 桶),会撞进同一个星团 |

### 3.2 协调方式(只适用于方案 B)

1. **收稿与存证分离**。投稿走一个独立收件箱,复用反馈后端的形态:只存正文、署名、授权勾选和接收时间,不存 IP。它不进认领台账,也不碰 `/api/claim`。用户协议要新增一段专门说明投稿内容会被保存、谁能看到、多久删除,不能借用「诗文只存在浏览器」那句话。
2. **精选后静态入库**。入选稿件由站长写进 `shiyun-corpus` 的独立文件(例如 `curated/submissions.jsonl`,`provenance.type = "submission"`,附授权记录),随常规勘误重建一起上线。站点仍然是纯静态。
3. **不进双射字库,不改 N**。投稿诗放在独立图层(例如 `ugc/`)里,**不参与** `charset.json` 的频次排序和扩充,所以 N 和所有现有编号保持不变。
   - 正文的字全在字库里:这首诗在虚空里**本来就有**固定编号(编号只由文字决定)。投稿等于给这个坐标署了名,可以直接显示编号。
   - 有字库外的字:不显示编号,沿用探诗「自由模式」里对字库外字的提示,而不是扩字库。
4. **独立命名空间,不进 `poets.index`**。投稿人不生成 `fnv32(name|dynasty)` 形式的 poetId,改用 `u:` 前缀 id,独立渲染成一个「投稿星群」图层,避免和真实诗人撞名。
5. **检索分开**。投稿诗进不进寻诗索引由站长选择;要进的话单独出分片,不混进 `lines/` 和 `search/`。

方案 C(公开即时发布)和「语料全静态」从根本上冲突,需要真正的写入后端、审核后台和下架流程,本文不展开设计。

## 4. 滥用与审核工作量

### 4.1 已经发生的

- 反馈接口 #94–#125 中,8–9 月共 30 条测试和 XSS 探测(`<script>alert(1)</script>`、`<img src=x onerror=…>`、`<svg onload>`、`javascript:`、HTML 实体编码绕过等),明显是有人在系统化地探测。
- 这些探测目前**没有造成危害**,原因是:反馈只有站长通过 token 以 NDJSON 读取,从不在网页上渲染;前端用 React 渲染文本,默认转义。
- 现有防护偏弱:进程内限流按 UA 分桶,每 10 分钟 30 条,而 UA 可以随便伪造;nginx 对 `/api/feedback` **没有** `limit_req`(认领接口有)。

### 4.2 开放投稿后的风险增量

| 风险 | 方案 B | 方案 C |
|---|---|---|
| 存储型 XSS | 低:稿件不在页面上展示,入库前经站长人工处理 | 高:任何展示面都必须严格转义,包括分享卡、OG 和留影 |
| 违法有害内容 | 低:人工把关,不入选就不出现 | 高:先发后审会有窗口期;先审后发则延迟和工作量都上来 |
| 抄袭或冒名(把已出版的诗当自己的投) | 中:入库前要检索比对 | 高 |
| 刷量和垃圾稿 | 中:需要 nginx `limit_req` 加长度上限 | 高 |

### 4.3 方案 B 的最低防护清单(开放前必须做)

1. nginx 给投稿接口加 `limit_req`(参照认领接口:每 IP 每分钟几次),同时给 `/api/feedback` 补上同样的限流。
2. 服务端只接受纯文本:限制长度(比如正文 ≤ 2,000 字、署名 ≤ 20 字),拒绝任何带 `<` `>` 的署名;入库时再做一次 NFC 规范化和控制字符清理。
3. 收件箱容量上限,满了返回 503(反馈后端已经这样做)。
4. 投稿页写清楚:投稿不等于收录;授权条款(非独占、可撤回);禁止投他人作品。
5. 站长审稿流程:用寻诗和外部搜索查是否抄袭,再做内容判断,入选的写进 `curated/`。

### 4.4 工作量估计

按每月几条到几十条、每条 3–5 分钟(读稿、查重、判断)计算,**每月约 0.5–2 小时**。入选稿件随勘误重建一起上线,不需要单独部署。风险在于一旦被视频带火,一天可能来几百条,这时只能关入口或者积压,所以入口要有一键关闭的开关。

## 5. 方案对比

| | A 不开放 | B 只收稿、人工精选、静态入库 | C 公开发布 |
|---|---|---|---|
| 开发成本 | 0 | 中:收件箱接口、投稿表单、协议文案、语料投稿层、前端投稿星群 | 高:写入后端、审核后台、下架、展示面安全加固 |
| 运维成本 | 0 | 每月 0.5–2 小时审稿 | 持续审核,有窗口期风险 |
| 与红线和静态架构 | 无冲突 | 可协调(§3.2),需要改用户协议 | 根本冲突 |
| 对编号 / N | 无影响 | 设计上零影响(独立图层) | 同 B,但实现更难 |
| 合规风险(大陆) | 最低 | 低到中(不公开展示,站长把关) | 高 |
| 满足用户诉求 | 否 | 部分满足(能被收录,但不是人人都能发) | 完全满足 |

### 建议

1. **现在**:维持 A。公告里只说「看到了、在考虑、暂未开放」,不做承诺(本期公告已按这个口径写)。
2. **如果想试**:走 B,按下面的顺序做:
   1. 补齐 §4.3 的防护(包括给现有 `/api/feedback` 补 nginx 限流,这条不管开不开投稿都该做);
   2. 修改用户协议的隐私和授权段落;
   3. 做语料侧投稿层和前端「投稿星群」;
   4. 先做一期「征稿」(限时、限量),观察实际稿量和质量,再决定要不要常设。
3. **方案 C 不建议**:它和诗云纯静态、零写入的架构根本冲突;面向 85% 大陆访客做公开 UGC 发布,在合规上处于最不利的位置。
